```md
## 怎么做

1. 根据目标总时长拆分片段。
2. 为每个片段准备对应提示词。
3. 第一段使用初始参考图。
4. 后续片段以上一段末帧作为连续性参考。
5. 检查输出片段后再决定是否继续增加总时长。

## 容易踩坑

- **主体在后续片段发生明显变化** → 检查上一段末帧是否正确作为下一段参考。
```

这里使用“怎么做 / 容易踩坑”是因为视频本身是操作教程，不代表它们是固定章节。来源入口放在“先看结论”后、正文前；播放器不再使用额外“视频资料”标题。资料获取提示、UP 主资源与视频简介都采用紧凑形式，完整原始简介以“UP 主原文（完整说明与链接）”继续折叠。

## 示例 B：结构片段库（不是目录模板）

知识密集型内容仍应先在 runtime 建立原子事实清单，再合并成 `knowledge_outline`。但 `knowledge_outline` 只是事实保护清单，不是最终文章目录；写正文前还要根据事实之间的对象、因果、流程、比较、前提和使用场景做自然聚类。

下面只展示几种**互相独立的结构片段**。它们用于说明 Markdown / Learning Lab 组件如何服务不同信息关系，不能被拼成一篇固定目录，也不能据此推断“知识密集型视频应该有几章”。

### B1：节点 / 插件更新，按真实变化组织

```md
## 新增能力

- 新增能力 A：……
- 新增能力 B：……

## 使用前提

| 前提 | 要求 |
| --- | --- |
| 版本 | …… |
| 依赖 | …… |

## 兼容与限制

> [!risk] 使用前确认
> 只保留真正会影响安装、运行或结果的冲突与限制。
```

这里自然形成三个主题，是因为来源本身存在“变化 → 前提 → 限制”的关系；如果某个视频只讲新增能力和安装方式，就不应为了凑数补出第三章。

### B2：横向比较，一个主章节也可以成立

```md
## 方案怎么选

| 方案 | 适合场景 | 关键优势 | 限制 / 代价 |
| --- | --- | --- | --- |
| A | …… | …… | …… |
| B | …… | …… | …… |
| C | …… | …… | …… |

> [!risk] 不要混用的组合
> 如果来源明确给出互斥或冲突关系，在表格后单独强调。
```

比较关系已经被一张表完整表达时，不需要把每个方案再拆成独立 H2。

### B3：短知识视频，可以不人为制造 H2

```md
- **核心结论**：……
- **直接可用值**：……
- **适用条件**：……
```

如果内容只有一个稳定主题，列表比“为了像一篇文章而拆成多个章节”更合适。

### B4：模型百科，只展示局部结构，不给完整标准目录

```md
## 模型路线

> [!grid-2]
>
> > [!card] FL2VA
> > **适合**：……
> >
> > **限制 / 特点**：……
>
> > [!card] Ref2VA
> > **适合**：……
> >
> > **限制 / 特点**：……

## 性能实测

| 配置 / 条件 | 耗时 | 质量变化 | 结论 |
| --- | --- | --- | --- |
| …… | …… | …… | …… |
```

这只是两个可能的自然主题片段，不代表模型百科只能写这两章，也不代表还必须补“核心规格 / 输入 / 加速 / 提示词”等固定章节。只有来源中形成稳定语义组的事实才升级为 H2。

### B5：少章节不等于少知识

同一个自然章节可以同时承载路线判断、成员关系、可直接使用值和实测证据：

```md
## 加速与取舍

> [!grid-3]
>
> > [!card] 注意力优化
> > 适合作为低损耗基线……
>
> > [!card] 低步数 LoRA
> > 速度提升明显，但必须匹配步数……
>
> > [!card] Cache / Prediction
> > 跳过计算，质量与稳定性代价最大……

### LoRA 成员与兼容关系

| 成员 | 来源 / 兼容 | 建议步数 | 取舍 |
| --- | --- | --- | --- |
| …… | …… | …… | …… |

### 实测证据

| 配置 | 耗时 | 质量变化 / 失败表现 |
| --- | --- | --- |
| …… | …… | …… |

> [!risk] 冲突
> 明确写出互斥组合和实际影响。
```

这里仍然只有一个 H2，但没有把具体成员、配置、耗时和失败表现压成一句概括。**章节数量只影响分组，不影响事实保留预算。** 内容完成后才进行这种排版转换；Layout Pass 不负责再次摘要。

知识密集型笔记可以用表格、Grid、Chip 等压缩版面，但不能通过“只留类别名”来压缩事实。比如保留 `larryvrh · drbaph · Abiray · LightX2V` 还不够；如果字幕明确讲了它们之间的来源、原生兼容或 4 / 8 步对应关系，这些关系也必须进入正文。

## 质量判断

无论采用哪种结构，都必须满足：

- 事实只来自当前字幕与 UP 主原始简介；Learning Lab、模型记忆、联网查询或第三方下载资料不自动并入本视频笔记；
- 高价值参数、限制、比较、专名、兼容性和重要资源不能因为追求简短而丢失；
- 知识密集型内容先完成 Fact Ledger，再形成 `knowledge_outline` 与 Semantic Draft，避免“主题正确、细节关系丢失”；
- Semantic Draft 内容完整后才做 Layout Pass；排版只能转换表达形式，不能再次摘要或删减事实；
- 如果来源只说明“三连 / 充电 / 评论关键词”等条件后可领取资料，只记录获取条件与来源原话；资料本体未采集到时不得由智能体补写；
- 不确定的信息宁可省略或判定来源不足，不得用模型常识补全；
- 成稿后必须重新回到原 transcript 做覆盖复核，不能只检查自己生成的 outline；
- runtime 的 `analysis.json`、marker、内部路径和采集状态不进入正式笔记。
