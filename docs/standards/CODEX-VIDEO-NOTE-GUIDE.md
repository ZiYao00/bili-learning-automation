# B站视频转笔记：内容与质量标准

> 本文件主要服务 `workflow_mode: strict`。默认 `light` 模式只需执行 `LIGHT-WORKFLOW.md`，不要加载本文件的全部过程规则。

## 目标

把高质量字幕与 UP 主原始简介整理成可长期保存、检索和复用的 Obsidian 学习资料，而不是只生成一段摘要。

默认同时满足两层需求：

- 顶部“先看结论”用于 30 秒内判断视频价值；
- 下方知识正文保留真正值得以后查阅的具体知识。

简单视频应保持简洁；知识密集型视频允许更长。不要为了统一格式牺牲信息价值。

## 责任边界

### 程序负责，智能体不得修改

- Frontmatter；
- 收集阶段 H1 与 H1 下方“作者 · 发布日期 · 时长 · BVID”元信息行；
- 视频简介、UP 主资源、条件资料获取提示与原始简介；
- 位于“先看结论”后、知识正文前的 Bilibili iframe 与来源区；
- tags；
- 文件路径和文件名；
- runtime 草稿中的 AI marker；
- runtime `analysis.json` 的基础结构；
- runtime `fact-ledger.md`、`semantic-draft.md`、`layout-plan.md` 脚手架及其路径。

### 智能体负责

1. 判断字幕与简介是否足以支撑可信学习笔记；
2. 知识密集型内容完成 Fact Ledger，再形成 `knowledge_outline`；
3. 在 Semantic Draft 中先完成知识内容；
4. 内容完成后独立执行 Layout Pass；
5. 填写短的“先看结论”和完整动态知识正文；
6. 最终排版后回到 transcript 做 Source Recheck；
7. 完成 `coverage_review`。

不要重新生成整篇 Markdown，也不要改动程序确定性部分。

## 来源充分性

字幕不是视频本身。特别是 ComfyUI 等技术视频，关键节点名、参数、连线或画面演示可能只存在于屏幕中。

不要用固定时长或字符数简单决定质量。结合上下文判断：

- 字幕是否连续、是否大面积缺失或乱码；
- 专有名词是否严重损坏到无法确认；
- 简介宣称的重要主题是否能在字幕中找到对应内容；
- 是否大量出现“这里、如图、这个参数、按这样连接”等只能依赖画面理解的表达；
- 是否能仅凭现有文本确认主要结论、方法、参数、限制、比较和重要资源。

来源不足时宁可停止。不得用模型记忆或常识补齐缺失的具体事实。

## 内容证据边界

正文事实必须来自：

- 当前视频字幕；
- UP 主原始简介。

用户额外提供的资料只有在明确要求写入时才能加入，并标记为“用户补充”。

不能根据常识补全字幕没有提供的参数、资源地址、版本、结论或兼容关系。视频字幕可能来自音频自动转写；遇到受转写噪声影响的专有名词时，按三级处理：来源能确认则使用可确认写法；高度疑似但无法确认则保留“字幕原音 / 名称未确认 / 待核实”等检索线索；完全无法判断则保留仍可确认的用途、关系、参数或实测结果并省略具体拼写。不得把低置信名称静默升级成确定事实，也不得仅因名称受损就删除与之关联的高价值知识。对于“三连 / 充电 / 评论关键词 / 私信 / 进群后领取模板、工作流或资料”这类信息，只保留来源明确支持的获取条件与原始说明；资料本体没有被采集到时，不得由智能体自行生成或猜测。

## 高价值信息保护

以下内容如果与视频主题有关，应优先保留，不能仅为了缩短篇幅而删除：

- 参数、数值、公式、数量和上下限；
- 模型、节点、插件、LoRA、格式、版本等专有名词；
- A/B 区别、适用条件和兼容性；
- 作者明确推荐与质量/速度/稳定性权衡；
- 会影响结果的前提、例外、冲突和警告；
- 结构化方法、提示词公式、关键工作流；
- 视频明确给出的运行入口、版本/安装前提与关键组件职责；
- 具有长期参考价值的实测案例：使用条件、配置、耗时、质量变化或失败表现之间的关系；
- 视频明确提供且具有学习价值的资源地址。

这是语义保护，不要求逐字抄字幕。可以合并、表格化、去重和改写。

还要特别避免两类“二次压缩”：

- **类别保住、成员丢失**：如果作者专门盘点了一组具有检索、安装、识别或比较价值的插件 / LoRA / Cache / 模型，不要只留下“还有其他方案”或一个大类名称；可以改用 Table / Chip 压缩版面，但应保留值得以后搜索的具体成员。
- **原则保住、可直接使用值丢失**：当视频同时给出“约 1MP”这类原则和 `960×544` 这类典型可直接使用值时，两层信息都应保留；前者帮助理解，后者帮助实际操作。
- **结论保住、证据丢失**：如果视频用一组实际配置说明“为什么更快 / 更慢、为什么更软 / 更稳”，不要只留下“速度与质量需要权衡”。应保留足以复查取舍的条件与结果；广告价格、纯活动口播仍可省略。

也不要机械保留所有数字。广告价格、活动优惠、与学习目标无关的口播数据等是否进入正文，由智能体根据长期参考价值判断。

## Fact Ledger 与知识索引

来源充分后，知识密集型内容先完成 runtime 的 `fact-ledger.md`，再填写 `analysis.json` 的 `knowledge_outline`。

Fact Ledger 是具体事实与关系的保全层；`knowledge_outline` 只是上层索引，不是事实清单、最终文章目录或知识图谱，条目与最终 H2 **不存在一一对应关系**。它们的作用是：

- 防止长字幕前半部分的重要信息在写作阶段被遗忘；
- 给成稿后的覆盖复核提供检查基线。

短且简单的视频可以简化 Fact Ledger；长视频、百科型、参数密集或实测证据多的内容应完整使用。

Fact Ledger 应按 transcript chunk 或自然主题记录原子事实，显式保留具体成员、数值/上下限、版本、A/B 关系、来源/继承、适用条件、例外、冲突、兼容性和作者评价。若视频讲解了实际落地，还要记录运行入口、版本/插件安装条件、组件职责，以及“配置 → 耗时 / 质量结果 / 失败表现”的证据链。“模型选择 / 提示词 / 加速方案”只是主题标签，不能代替事实。**可以压缩表达，不要在知识提取阶段压缩事实关系或证据链。**

新任务的三份工作文件必须按 `KNOWLEDGE-DENSE-WORKFLOW.md` 更新 `workflow_status`：知识密集型 Fact Ledger、Semantic Draft、Layout Plan 均应为 `complete`；短且简单的视频仅 Fact Ledger 可标记为 `not_applicable`，并必须填写 `workflow_reason`。状态仍为 `pending`、文件为空模板或路径越界时，finalizer 拒绝发布。

## Semantic Draft：先完成内容，再形成最终正文

Fact Ledger 完成后，先在 runtime `semantic-draft.md` 写内容完成稿。观察原子事实之间的**共同对象、因果链、操作流程、比较关系、前置条件、例外与使用场景**，再做自然聚类。只有形成稳定语义组的内容才升级为 H2；一个 H2 可以吸收多个事实与 outline 条目，并通过 H3、表格和列表继续承载细节。在原始事实、参数、比较与实测证据已经完整保留的前提下，可以额外提炼由当前来源共同支持的能力边界、因果关系或选择原则；这种提炼是增量解释，不能替代支撑证据、删减原始条件或引入来源之外的新知识。

没有“目标章节数量”。章节数量只决定事实如何分组，**不得改变事实保留预算**。不得因为同属 H3、模型百科、节点更新或知识密集型内容，就预设 3 / 4 / 5 个章节；也不得为了凑齐章节数量拆开一个自然主题，或因为减少 H2 就同步删掉参数、成员、关系与实测证据。章节标题、数量和长短应能从当前视频的信息关系本身解释出来，而不是从示例或上一份笔记推导出来。

`STANDARD-VIDEO-NOTE-EXAMPLE.md` 只提供局部语法与关系表达，不提供可复制的章节集合或组件组合。知识密集型完整流程见 `KNOWLEDGE-DENSE-WORKFLOW.md`。

## 长字幕处理

当一次性阅读容易遗漏时，可以按语义章节、主题变化或合理时间段分段提取，再合并去重。知识密集型视频优先逐块建立事实清单，最后统一去重和组织；不要边读边直接写最终正文，否则前半段的具体参数和成员关系最容易在后半段被抽象掉。

不要把固定 Map-Reduce 流程强加给所有视频，也不要只按固定 token 数机械切块；如果必须按长度切分，应保留足够上下文，避免知识点跨块后失去含义。

## 先看结论

保持短而有用，只写读者真正需要快速知道的**结论、选择、关键参数、限制、风险和适用场景**。建议包含：

- 视频主要解决什么问题；
- 适合什么需求；
- 最值得记住的核心结论。

不要使用“本文覆盖……”“本笔记包含……”“接下来介绍……”这类目录式或元描述式摘要，也不要在这里重复完整正文。

## 知识正文

正文结构完全由视频内容决定。

可以使用：

- 分级标题；
- 表格；
- 项目列表；
- 编号步骤；
- Obsidian Callout；
- 少量时间点链接。

不要强制出现“怎么做 / 容易踩坑 / 我来实践”。操作教程可以有步骤；模型百科可以按规格、输入方式、对比、提示词、加速、兼容性组织；横向对比可以使用比较表；故障排查可以按症状、原因、判断和解决方案组织。

格式应服务信息，而不是让所有视频看起来像同一个模板。

当来源明确介绍一组并列对象（例如 `Top N`、项目 / 工具 / Skill / 模型清单）时，默认按来源出现顺序使用连续编号 `01 → N`，概览表与详细标题复用同一编号，不因主题聚类、能力链或后续分析打乱主序列。若来源明确提供对象的外部 URL，概览表和详细标题中的对象名称应直接挂 Markdown 超链接；没有明确 URL 时保持纯文本，不根据模型记忆猜链接。能力链、分类、对比关系可以另用 Callout / Table 提炼，但只作为补充关系层，不能替代或重排连续编号正文。

## 视觉与版式决策

只有 `semantic-draft.md` 内容完成后，才进入 runtime `layout-plan.md` 与 Layout Pass。Layout Pass 只能把已经完整的内容转换成更合适的表达形式，不能承担第二次摘要、重新选择事实或为了页面整齐删减信息。排版前后的高价值事实必须一一对应。

视频学习笔记复用 ComfyUI Learning Lab Design System 的语义组件。Agent 只负责在 Markdown 中选择合适的表达，CSS 负责视觉表现；关闭 CSS 后正文仍必须可读。

先判断内容关系，再决定版式：

| 内容关系 | 优先表达 |
| --- | --- |
| 当前最重要的选择、结论、默认策略 | `[!summary]`；整页只保留一个最高优先级 Summary |
| 2 个需要直接比较的对象 | `grid-2 + card` 或对比表；有固定比较字段时优先表格 |
| 3 个平级路线 / 模式 | `grid-3 + card` |
| 4 个以上对象或多字段比较 | Table |
| 一组名称需要保留、但每个都不值得展开 | Chip |
| 明确风险、冲突、兼容性问题、不推荐路线 | `[!risk]` |
| 来源限制、背景说明、验证状态 | `[!meta]` |
| 与当前知识点直接相关的 GitHub、模型、工作流或深入阅读入口 | `[!resource]`；不要把程序已保留的整份 UP 主资源清单再复制一遍 |
| 不存在明显并列 / 比较关系 | 普通标题、段落和列表 |

不要为了“好看”把所有内容卡片化；Card 主要解决并列关系和空间比较。Badge 只表达短状态，不承载正文。允许使用 Learning Lab 现有的少量视觉 HTML 原语（如 `ll-badge`、`ll-chip`），但不要用 HTML 重写标题、表格和正文段落。

### Grid 与 Card 的强制嵌套语法

`grid-2`、`grid-3` 和 `grid-auto` 是外层布局 Callout；`card` 必须是它的**嵌套子 Callout**。子卡片必须使用双层 `> >`，不能使用单层 `> [!card]`：

```md
> [!grid-3]
>
> > [!card] 路线 A
> > 内容……
>
> > [!card] 路线 B
> > 内容……
>
> > [!card] 路线 C
> > 内容……
```

错误的单层写法会让 Obsidian 无法建立“网格 → 卡片”的组件结构，导致 `[!grid-3]` 暴露或卡片不完整；finalizer 会拒绝直接以 `> [!card]` 开始的正文。

知识密集型长笔记如果存在 4 个以上稳定大章节，可考虑使用 `01 ·`、`02 ·` 这类 H2 编号方便回看定位；短视频不强制编号。

正式阅读顺序固定为：**标题 / 元信息 → 先看结论 → 播放器与来源区 → 动态知识正文**。播放器直接跟在“先看结论”后，不显示额外“视频资料”标题；资料获取提示保持紧凑 Callout，UP 主资源使用逐条 Markdown 链接列表，视频简介压成紧凑段落，完整原始简介以“UP 主原文（完整说明与链接）”继续折叠。这样先交代来源与资源，再进入较长知识正文，同时减少资料区的纵向层级。

## 覆盖复核

最终排版后必须重新按 manifest 顺序抽查或复读原 transcript；`knowledge_outline` 只能作为辅助索引，不能代替回看原字幕。知识密集型视频还应同时对照 `fact-ledger.md`、`semantic-draft.md` 与最终正文。至少检查：

- 重要参数、公式、限制、比较、方法是否进入正文；
- 同类成员是否只剩一个类别名，或只留下名称却丢了来源、继承、步数、兼容性等关系；
- 比较关系是否只保留了一边；
- 原则性结论是否把视频给出的可直接使用值一起压掉；
- 默认值后面的例外条件是否丢失；
- 多个方案是否被错误合并；
- H2 数量减少时，参数、成员、关系和实测证据是否也被同步压掉；
- Layout Pass 前后的高价值事实是否一一对应，是否为了卡片数量或页面简洁重新摘要；
- 运行入口、版本/安装前提和关键组件职责是否因被误当作背景口播而删除；
- 实测案例是否只剩“更快 / 更慢、质量更好 / 更差”的概括，而丢失可判断取舍的条件与结果；
- 是否为了“简洁”删掉高价值具体知识；
- 是否新增了字幕/简介没有支持的事实。

复核通过后填写 `coverage_review.status = "passed"` 和简短 notes。

程序只验证这个流程确实完成，不把 Markdown 非空误当作知识完整。

## 文件名、标题与收件箱

每次成功转换生成一篇笔记；同一视频允许再次转换，供重复学习或对比不同版本的整理结果。

收集阶段文件名：

```text
{原视频标题}.md
```

同名时使用 `（2）`、`（3）` 等序号防覆盖。BVID 不作为文件名后缀，与作者、发布日期、时长一起显示在 H1 下方的紧凑元信息行；重复 BVID 不阻止新的转换任务。

所有新笔记先进入 `00-待整理`，taxonomy 只提供 tags 与后续归档建议。

## Frontmatter 与视频简介

Frontmatter 固定由程序生成：

- `author`
- `published`
- `duration`
- `source`
- `tags`
- `cssclasses: [learning-page, video-note]`（实际 YAML 使用列表形式）

UP 主原始简介是硬性核心数据。智能体不得用 AI 摘要替代、修改原始语义、删去 UP 主资源链接，或把抓取失败当成“视频无简介”。展示层会从原始简介中提取真正的内容性概述；如果简介只有资源、栏目标题或分隔符，则省略“视频简介”小节，但原始简介仍以“UP 主原文（完整说明与链接）”在折叠区完整保留。

`UP 主资源` 的显示标题由程序确定性生成，不由智能体改写：保留原始资源标签与栏目上下文，并在原始简介已明确资源类型或 URL 平台时补足可识别信息。例如“涉及插件”下的 GitHub 链接显示为 `GitHub 插件 · MieNodes`，国际/国内站下同名“体验地址”保留为 `国际站 · 体验地址` / `国内站 · 体验地址`，夸克链接不会重复显示成 `夸克网盘（夸克网盘）`；重复 URL 在紧凑资源清单中只保留一项。无法可靠判断类型时保守保留原标签；完整原始简介始终在下方折叠区保留，并在输出前规范化 HTML entity，避免 `&amp;amp;` 之类二次转义。

## 机器资料边界

最终笔记不得出现：

- `.runtime` 路径；
- `job.json`；
- `analysis.json`；
- `agent_handoff.md`；
- `fact-ledger.md`、`semantic-draft.md`、`layout-plan.md` 等 runtime 工作文件名；
- Fact ID、内部证据编号或工作状态；
- Cookie；
- 抓取日志和采集状态。

## 完成判断

一篇正式笔记至少满足：

- 来源充分性已判断为 `sufficient`；
- `knowledge_outline` 已形成；
- `coverage_review` 已通过；
- 路径、文件名、H1、标题元信息、Frontmatter、播放器与来源区、iframe 和 tags 均通过确定性校验；
- “先看结论”和动态知识正文均已填写；
- 正式 Markdown 不含 runtime marker 和机器内部资料；
- finalizer 返回 `note_ready`。

在此之前不得声称完成。

## 回归基准

MiniMax H3 百科视频 `BV19K8F6PEzN` 用作知识密集型回归样本。最终不要求复制人工笔记原文，但应能识别并合理保留下列类型的内容：

- 推荐分辨率、帧数规则、时长与限制；除了“约 1MP / 最低约 0.4MP”这类原则，还应保留视频明确给出的典型可直接使用尺寸；
- 文本/图片/视频/音频输入能力；
- FL2VA 与 Ref2VA 的区别及数量限制；
- 提示词结构与 Ref2VA 六段式；
- SageAttention、Sol-Attn 与三条加速路线；
- 视频专门盘点的加速 LoRA 成员（如 larryvrh、drbaph、Abiray、LightX2V）不能被压成“若干 LoRA”；
- 视频专门盘点的 Cache / Prediction 成员（如 EasyCache、LazyCache、TeaCache、MagCache、FirstBlockCache、Spectrum）应保留可检索名称，并明确真正影响选择的冲突关系；
- 速度、质量、稳定性权衡及冲突关系；
- 官方便携包、整合包、云端镜像三种运行入口，以及官方便携包所述的 ComfyUI `0.31.0+` 前提；
- MieNodes、KJ Nodes、SolAttn_triton、Spectrum 的职责，以及字幕明确说明的 SolAttn_triton 手动安装限制；
- 视频给出的性能实例：H3 默认 `24fps`；4090 上 `960×544`、10 秒质量流程约 5 分钟；4 步 LoRA 示例约 84 秒但细节/质感下降；
- 视频明确提供的重要插件、模型与工作流资源。

如果最后仍然只剩“选模型 → 选工作流 → 写提示词 → 注意加速冲突”这类概要，应视为内容质量回归失败。
