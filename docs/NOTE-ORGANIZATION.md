# 学习后整理

本项目的新笔记始终先进入 `00-待整理`。整理功能**默认关闭**，只有用户明确要求“整理 / 归档笔记”时才进入本流程；不得把生成与整理合并成一步，也不得在 finalizer 完成后自动整理。

整理阶段负责两件事：

1. 判断这篇内容是否值得以完整学习笔记长期保存；
2. 根据判断执行普通归档，或把纯资源分享压缩进资源集合页。

> 生成阶段负责忠实记录；整理阶段负责长期价值筛选。

---

## 1. 先完整阅读，再判断类型

整理时先完整阅读目标笔记，不根据文件名、旧 Tags 或 taxonomy 关键词直接批量猜分类。

只做三个宽松判断，不把它们写成前置生成标签：

- **知识型**：去掉下载链接后，仍有值得长期复习的方法、参数、原理、实测、选择条件或教程内容。
- **混合型**：既有资源，也有明显的长期学习价值。
- **纯资源型**：主要价值是“发现一个资源并去获取/使用”，删除资源名称、功能、获取方式后基本没有值得长期复习的内容。

最重要的判断问题是：

> **把资源链接删掉以后，这篇内容还有没有长期学习价值？**

有，就按知识型 / 混合型保留完整笔记；基本没有，才进入纯资源压缩。

参考：

- MiniMax-H3 Motion Context 长视频续接教程 → 知识型 → 保留完整笔记。
- JMAI+H3 17 分钟完整流程，既有程序下载又有大量参数与使用技巧 → 混合型 → 保留完整笔记。
- “5 个 AI 审美网站”，主体只是 5 个网站及用途 → 纯资源型 → 压缩。
- VideoShotCraft 100+ 镜头配方，主体是 GitHub 项目及功能介绍 → 纯资源型 → 压缩。
- AI 电影 8 个 Skills，主体是资源发现、获取和安装包说明 → 纯资源型 → 压缩。

这些案例用于理解边界，不是固定关键词规则。允许 Agent 根据完整正文判断。

---

## 2. 普通归档：知识型 / 混合型

普通归档继续遵守原来的内容保护：

- 只改文件路径；
- 只改文件名；
- 重建 `99-导航`；
- **不得改写正文、Summary、H1、Frontmatter、Tags、视频简介、UP 主资源或测试标记。**

目录通常采用：

```text
领域 / 对象 / 笔记.md
```

目录最多两层。有明确模型、工具或项目时围绕对象聚合；没有稳定对象时可用主题作为第二层。不要为了套分类继续细分。

文件名应短、自然、有区分度。可以删除视频标题中的宣传语和无助检索的信息，但不要把摘要重新塞进文件名。`百科：`、`实测：`、`教程：`、`工作流：` 等只在确实更清楚时使用，不是固定模板。

`config/bilibili-note-taxonomy.json` 的 `routes` 只是建议，不是 Organizer 的强制分类表。

命令：

```powershell
bili-learning organize `
  --mode archive `
  --note '<现有笔记路径>' `
  --filename '<新的简短文件名>' `
  --destination '<领域/对象>' `
  --confirmed-scope '<single|latest|all>'
```

`archive` 是默认模式，因此 `--mode archive` 可省略。

同名目标不会覆盖，会自动使用 `（2）`、`（3）` 等序号。

## 3. 纯资源压缩：只在整理阶段执行

纯资源型不再继续保留“一条 B站视频 = 一篇长学习笔记”。整理时把它压缩成一张短资源卡，并合并到 `05-资源` 下的集合页。

默认资源根目录：

```text
05-资源/
```

集合页由内容自然选择，例如：

```text
05-资源/Skills.md
05-资源/网站与灵感.md
05-资源/AI工具与项目.md
05-资源/模型与LoRA.md
05-资源/工作流资源.md
```

不要预先建立大量空目录或空集合页。只有实际出现资源时才创建。

### 资源卡应该保留什么

Agent 完整阅读原笔记后，只保留真正帮助未来使用的信息：

```markdown
## VideoShotCraft

- **类型**：GitHub 项目 / 视频制作 Skill
- **功能**：使用预设镜头、动效和音乐节奏编排视频，可导出剪映工程继续修改。
- **适合**：口播包装、卡点视频、镜头动效、自动化剪辑。
- **获取**：https://github.com/...
- **状态**：待测试
```

字段不是固定表单。资源很简单时可以更短；资源复杂时允许补充安装位置、使用前提、下载位置、已测试结论等。

优先保留：

- 资源名称；
- 一句话功能；
- 适用场景；
- 获取地址 / 官方入口；
- 用户已经确认的下载、安装或测试状态；
- 对未来再次使用真正有帮助的少量说明。

通常删除：

- UP 主的宣传铺垫；
- 与长期使用无关的 Star 数、活动话术、夸张评价；
- 重复介绍；
- 纯粹为了完整而保留的视频复述。

### 状态建议

资源卡可按实际情况使用简单状态：

```text
待查看
待下载
已下载
待测试
在使用
已淘汰
```

不要凭空猜状态。只有原笔记或用户上下文能够确认时才写。

## 4. 资源卡草稿与核心边界

为了避免 CLI 接收长文本和误操作，Agent 不把资源卡正文直接放命令行。

先在：

```text
<runtime_root>/resource-cards/
```

写一份临时 Markdown 卡片，然后调用：

```powershell
bili-learning organize `
  --mode resource `
  --note '<现有笔记路径>' `
  --collection '<集合页名称>' `
  --card-file '<runtime_root>/resource-cards/<临时卡片>.md' `
  --confirmed-scope '<single|latest|all>'
```

核心只接受位于 `runtime/resource-cards` 下的卡片草稿，并限制长度。这样 Agent 可以负责语义判断和压缩，核心负责安全写入、合并、备份、删除原独立笔记和刷新导航。

资源集合页带有内部 marker，普通 BVID 重复检测会忽略集合页。这样以后再次发送同一个 B站链接时，生成阶段仍按正常流程创建完整待整理笔记；只有用户再次启动整理后，才决定是否更新对应资源卡。

同一 BVID 再次压缩到同一资源集合页时，会更新已有卡片，而不是追加重复卡片。

---

## 5. 原笔记保护与恢复

资源压缩会减少独立笔记数量，因此属于有损整理操作。核心在删除原独立笔记前，会把原文件完整复制到：

```text
<runtime_root>/organize-backups/
```

然后才写入资源集合页并移除原独立笔记。

普通 `archive` 不需要备份，因为它仍然使用不改写内容的移动逻辑。

`organize-backups` 是整理恢复用的运行时保护，不进入 Obsidian 导航。后续如要清理这些备份，应单独设计明确的保留策略，不在整理命令里自动批量删除。

---

## 6. 整理范围

范围共有三种：

- `single`：用户明确指定某一篇；
- `latest`：用户明确说“最近一篇”；Organizer 会验证它确实是 `00-待整理` 中最近的 Markdown 文件；
- `all`：用户明确要求整理全部待整理笔记；仍逐篇完整阅读和判断，不把批量整理变成机械套模板。

用户已经明确指定文件时直接使用 `single`。只有用户只说“整理笔记”且范围确实无法从上下文确定时，才询问范围。

整理默认关闭的门禁不得因为增加了资源压缩能力而放松。

---

## 7. 重复 BVID

普通归档会检测同 BVID 的其它独立笔记并提示，但不阻止归档、不覆盖、不删除、不自动合并。

资源集合页可以包含很多 BVID，因此不会被普通重复检测当成一篇视频笔记，也不能作为普通 `update` 的目标。

如果相同资源以后出现新版视频：

1. 正常生成完整待整理笔记；
2. 用户明确要求整理；
3. Agent 判断仍属于纯资源型；
4. 以新的完整笔记为依据生成资源卡；
5. 核心按 BVID 更新或追加集合页中的卡片。

不要在生成阶段直接修改资源集合页。

---

## 8. Junction 路径

当 Obsidian Vault 通过 Windows Junction 指向仓库笔记目录时，同一文件可能同时表现为逻辑 Vault 路径和真实磁盘路径。

Organizer 的 JSON 返回会同时给出逻辑路径和解析后的真实路径。出现 `M:` 与 `G:` 两种表现不代表重复写入。

---

## 9. 不做什么

整理阶段仍然不负责：

- 在生成阶段提前打 `knowledge / resource / mixed` 标签；
- 根据标题自动跳过完整笔记生成；
- 自动启动整理；
- 自动修改知识型或混合型正文；
- 自动改 Frontmatter / Tags；
- 自动合并知识型重复 BVID；
- 自动删除测试版本；
- 自动批量清理 `organize-backups`；
- 把纯资源压缩规则反向塞进采集或 finalizer。

这些边界是为了保持主生成链路简单、稳定，并把“是否值得长期保存”留给用户主动启动的整理阶段。
