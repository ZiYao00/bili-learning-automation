# 学习后整理

本项目的新笔记始终先进入 `00-待整理`。整理功能**默认关闭**，只有用户明确要求“整理 / 归档笔记”时才进入本流程；不得把生成与整理合并成一步，也不得在 finalizer 完成后自动整理。**普通整理仅改变目录：默认不改变文件名或 Markdown 任意字节。**

整理阶段负责两件事：

1. Agent 完整阅读笔记，确定最合适的目标归档目录；
2. 默认只移动完整 Markdown，保留原文件名和全部字节；
3. 只有用户另行明确请求**有损资源压缩**，才进入独立 `resource` 模式。

> 生成阶段负责忠实记录；默认整理阶段只负责分类归档和导航。**学习笔记、标题、摘要、Frontmatter、Tags、资源链接与排版均不修改。**

---

## 1. 先完整阅读，再判断类型

整理时先完整阅读目标笔记，不根据文件名、旧 Tags 或 taxonomy 关键词直接批量猜分类。普通归档对三种类型一律保留完整笔记；以下类型判断仅用于用户另行要求资源压缩时。

只做三个宽松判断，不把它们写成前置生成标签：

- **知识型**：去掉下载链接后，仍有值得长期复习的方法、参数、原理、实测、选择条件或教程内容。
- **混合型**：既有资源，也有明显的长期学习价值。
- **纯资源型**：主要价值是“发现一个资源并去获取/使用”，删除资源名称、功能、获取方式后基本没有值得长期复习的内容。

最重要的判断问题是：

> **把资源链接删掉以后，这篇内容还有没有长期学习价值？**

有，就按知识型 / 混合型保留完整笔记；基本没有，才进入纯资源压缩。

参考：

- MiniMax-H3 Motion Context 长视频续接教程 → 知识型 → 保留完整笔记。
- JMAI+H3 17 分钟完整流程，既有程序下载又有大量参数与使用技巧 → 混合型 → 保留完整笔记。
- “5 个 AI 审美网站”，主体只是 5 个网站及用途 → 纯资源型 → 压缩。
- VideoShotCraft 100+ 镜头配方，主体是 GitHub 项目及功能介绍 → 纯资源型 → 压缩。
- AI 电影 8 个 Skills，主体是资源发现、获取和安装包说明 → 纯资源型 → 压缩。

这些案例用于理解边界，不是固定关键词规则。允许 Agent 根据完整正文判断。

## 2. 普通归档：知识型 / 混合型

普通归档继续遵守内容保护：

- **只变更文件所在目录；默认保留原文件名，不自动去掉（2）（3）等编号。**
- 移动前后要求 SHA-256 一致，且源路径、目标目录、内部链接与重名冲突均须检查。
- 重建 `99-导航`；移动成功但导航失败需报告 `organized_navigation_pending`，不得说“笔记未移动”。
- **不得改写正文、Summary、H1、Frontmatter、Tags、视频简介、UP 主资源、排版或测试标记。**

目录通常采用：

```text
领域 / 对象 / 笔记.md
```

目录最多两层。有明确模型、工具或项目时围绕对象聚合；没有稳定对象时可用主题作为第二层。不要为了套分类继续细分。

**默认保持视频原标题和 Markdown 文件名原样不动。**仅在用户额外明确授权重命名时使用兼容参数 `--filename`；普通整理不生成或修改标题，也不自动删除文件名后缀。

`config/bilibili-note-taxonomy.json` 的 `routes` 只是建议，不是 Organizer 的强制分类表。

命令：

```powershell
bili-learning organize `
  --mode archive `
  --note '<现有笔记路径>' `
  --destination '<领域/对象>' `
  --confirmed-scope '<single|latest|all>'
```

`archive` 是默认模式，因此 `--mode archive` 可省略。省略 `--filename` 时**不会覆盖重名目标，也不会自动增加序号**，会返回冲突并保留原文件。历史显式 `--filename` 调用仍兼容旧式自动编号；Agent 普通整理不得主动使用。

## 3. 纯资源压缩：只在整理阶段执行

**纯资源压缩不属于普通整理**，只有用户另行明确授权时，才把独立笔记压缩成资源卡并合并到 `05-资源`；未授权时，纯资源笔记也仅按完整文件归档。

默认资源根目录：

```text
05-资源/
```

集合页由内容自然选择，例如：

```text
05-资源/Skills.md
05-资源/网站与灵感.md
05-资源/AI工具与项目.md
05-资源/模型与LoRA.md
05-资源/工作流资源.md
```

不要预先建立大量空目录或空集合页。只有实际出现资源时才创建。

### 资源卡应该保留什么

Agent 完整阅读原笔记后，只保留真正帮助未来使用的信息：

```markdown
## VideoShotCraft

- **类型**：GitHub 项目 / 视频制作 Skill
- **功能**：使用预设镜头、动效和音乐节奏编排视频，可导出剪映工程继续修改。
- **适合**：口播包装、卡点视频、镜头动效、自动化剪辑。
- **获取**：https://github.com/...
- **状态**：待测试
```

字段不是固定表单。资源很简单时可以更短；资源复杂时允许补充安装位置、使用前提、下载位置、已测试结论等。

`类型` 是例外：为了让资源库可以快速扫读，纯资源卡应优先使用小而稳定的类型词表：`Skill / 工具 / 项目 / 模型 / LoRA / 网站 / 工作流 / 插件 / 数据集 / 文档`。一个资源通常写 1 个类型，确实同时属于两类时最多写 2 个，例如 `项目 / Skill`。不要把“视频编排、电影感、AI 创作”等用途描述塞进类型字段，这些放到“功能 / 适合”里。

优先保留：

- 资源名称；
- 一句话功能；
- 适用场景；
- 获取地址 / 官方入口；
- 用户已经确认的下载、安装或测试状态；
- 对未来再次使用真正有帮助的少量说明。

通常删除：

- UP 主的宣传铺垫；
- 与长期使用无关的 Star 数、活动话术、夸张评价；
- 重复介绍；
- 纯粹为了完整而保留的视频复述。

### 状态建议

资源卡可按实际情况使用简单状态：

```text
待查看
待下载
已下载
待测试
在使用
已淘汰
```

不要凭空猜状态。只有原笔记或用户上下文能够确认时才写。

## 4. 资源卡草稿与核心边界

为了避免 CLI 接收长文本和误操作，Agent 不把资源卡正文直接放命令行。

先在：

```text
<runtime_root>/resource-cards/
```

写一份临时 Markdown 卡片，然后调用：

```powershell
bili-learning organize `
  --mode resource `
  --note '<现有笔记路径>' `
  --collection '<集合页名称>' `
  --card-file '<runtime_root>/resource-cards/<临时卡片>.md' `
  --confirmed-scope '<single|latest|all>'
```

核心只接受位于 `runtime/resource-cards` 下的卡片草稿，并限制长度。这样 Agent 负责语义判断和压缩，核心负责安全写入、合并、备份、将原独立笔记移入 Windows 回收站和刷新导航；**回收站不可用时绝不回退永久删除**。

资源集合页带有内部 marker，普通 BVID 重复检测会忽略集合页。这样以后再次发送同一个 B站链接时，生成阶段仍按正常流程创建完整待整理笔记；只有用户再次启动整理后，才决定是否更新对应资源卡。

同一 BVID 再次压缩到同一资源集合页时，会更新已有卡片，而不是追加重复卡片。

## 5. 原笔记保护与恢复

资源压缩会减少独立笔记数量，因此属于有损整理操作。核心在删除原独立笔记前，会把原文件完整复制到：

```text
<runtime_root>/organize-backups/
```

然后才写入资源集合页并尝试将原独立笔记移入 Windows 回收站。失败时恢复集合页原状态并保留原笔记；暂不提供跨平台永久删除降级。

普通 `archive` 不需要备份，因为它仍然使用不改写内容的移动逻辑。

`organize-backups` 是整理恢复用的运行时保护，不进入 Obsidian 导航。后续如要清理这些备份，应单独设计明确的保留策略，不在整理命令里自动批量删除。

---

## 6. 整理范围

范围共有三种：

- `single`：用户明确指定某一篇；
- `latest`：用户明确说“最近一篇”；Organizer 会验证它确实是 `00-待整理` 中最近的 Markdown 文件；
- `all`：用户明确要求整理全部待整理笔记；Agent 仍逐篇完整阅读并生成分类计划，核心程序依据计划批量执行，不把分类变成关键词机械匹配。

用户已经明确指定文件时直接使用 `single`。只有用户只说“整理笔记”且范围确实无法从上下文确定时，才询问范围。

整理默认关闭的门禁不得因为增加了资源压缩能力而放松。

---

## 7. 重复 BVID

普通归档和批量预览会检测同 BVID 的其它独立笔记。兼容的单篇显式归档只提示；新批次默认跳过整个重复组，不覆盖、不删除、不自动选版本。重复清理由独立 `organize-duplicates` 显式计划控制。

资源集合页可以包含很多 BVID，因此不会被普通重复检测当成一篇视频笔记，也不能作为普通 `update` 的目标。

如果相同资源以后出现新版视频：

1. 正常生成完整待整理笔记；
2. 用户明确要求整理；
3. Agent 判断仍属于纯资源型；
4. 以新的完整笔记为依据生成资源卡；
5. 核心按 BVID 更新或追加集合页中的卡片。

不要在生成阶段直接修改资源集合页。

---

## 批量归档入口（默认只读）

1. `organize-list --scope all` 只读枚举 `00-待整理` 的文件、BVID 和 SHA-256。指定单篇时使用 `--scope single --note <文件路径>`。
2. Agent 完整阅读每篇目标笔记，自主判断目录，不按照标签、模型名称或 taxonomy 建议直接强制归类。
3. Agent 在 `<runtime_root>/organize-plans/` 下保存已审阅计划，JSON 内容例如：

```json
{
  "schema_version": 1,
  "notes": [
    {"source": "00-待整理/某个视频标题.md", "destination": "01-视频/MiniMax-H3", "sha256": "<64位真实哈希>"}
  ]
}
```

4. `organize-batch --plan '<计划路径>' --confirmed-scope all` 只预览；需用户已授权同一批次后添加 `--apply` 执行。核心逐篇校验哈希、目录、BVID、重名和内部链接，跳过冲突文件，不自动改名或删除。
5. 逐篇状态写入 runtime `organize-batches`。中断后沿用**同一份未改的计划**再次执行 `--apply`，识别已移动或硬链接已建立的中间状态，并重建导航。不得提前清理检查点。

每项只接受源相对路径、目标相对目录与原 SHA-256；不允许包含新文件名。单批最多 500 篇。首次采用 `all` 的计划必须覆盖当前待整理目录全部文件；已在执行中的计划可以恢复原批次，不会自动包含之后新到的笔记。无法确认不会导致断链时，默认跳过并报告，而非擅自更改其他笔记。

## 重复版本治理（独立、显式）

- `organize-duplicates --bvid <BV号>`：只读列出该 BVID 的所有独立笔记及哈希。
- Agent 依据用户明确选择的保留版本及待清理版本，在 `runtime/organize-plans/` 中写 JSON，字段为 `schema_version: 1`、`bvid`、`keep: {path, sha256}`、`recycle: [{path, sha256}]`。
- `organize-duplicates --plan '<计划路径>'` 只预览；加 `--apply` 后才逐文件移入 **Windows 回收站**，绝不猜最新版本或回退永久删除。
- 执行中持续校验 BVID、保留文件和回收文件哈希及内部链接；异常停止后续回收，并记录已经成功的项目。
- 默认 `organize` / `organize-batch` 不自动清理重复版本，也不触发有损资源压缩。

## 8. Junction 路径

当 Obsidian Vault 通过 Windows Junction 指向仓库笔记目录时，同一文件可能同时表现为逻辑 Vault 路径和真实磁盘路径。

Organizer 的 JSON 返回会同时给出逻辑路径和解析后的真实路径。出现 `M:` 与 `G:` 两种表现不代表重复写入。

---

## 9. 不做什么

整理阶段仍然不负责：

- 在生成阶段提前打 `knowledge / resource / mixed` 标签；
- 根据标题自动跳过完整笔记生成；
- 自动启动整理；
- 自动修改知识型或混合型正文；
- 自动改 Frontmatter / Tags；
- 自动合并知识型重复 BVID；
- 自动删除测试版本（仅在用户明确选择保留版与待回收文件并单独执行时，才可移入 Windows 回收站）；
- 自动批量清理 `organize-backups`；
- 把纯资源压缩规则反向塞进采集或 finalizer。

这些边界是为了保持主生成链路简单、稳定，并把“是否值得长期保存”留给用户主动启动的整理阶段。
