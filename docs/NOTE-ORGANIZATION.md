# 学习后归档

本项目的新笔记始终先进入 `00-待整理`。学习后归档默认关闭，只有用户明确提出“整理 / 归档笔记”时才执行。

归档阶段只解决两件事：

1. 这篇笔记应该放到哪里；
2. 文件名怎样更短、更容易识别。

**归档阶段不得修改笔记内容。** H1、Summary、正文、Frontmatter、Tags、视频简介、UP 主资源、`(workbuddy)` / `(GPT)` 等测试标记全部保持原样。

---

## 1. 核心原则

使用一条简单规则：

> **目录管“它属于谁”，文件名管“它是什么”，Tags 继续保留笔记生成阶段已经写好的知识维度。**

不要把目录做成百科分类树。默认采用：

```text
领域 / 对象 / 笔记.md
```

其中 `领域 / 对象` 最多两层目录。

例如：

```text
02-图像/
└─ Krea2/
   ├─ 百科：Krea-2 生图模型全解.md
   ├─ 教程：Krea-2 图像编辑.md
   └─ 实测：Krea-2 LoRA 效果.md
```

这比：

```text
02-图像生成/05-模型与LoRA/...
```

更容易浏览，也避免一篇综合笔记同时涉及模型、LoRA、ControlNet、提示词和图像编辑时出现分类争议。

---

## 2. 目录怎么判断

Agent 在归档前完整阅读笔记，然后只判断一个浅层目标目录。

优先按明确对象聚合：

```text
01-视频/MiniMax-H3
01-视频/Seedance
01-视频/Wan
02-图像/Krea2
02-图像/Qwen-Image
02-图像/Z-Image
03-LLM/Agent
03-LLM/本地模型
04-写作/AI写作
```

如果没有稳定对象，可以使用主题作为第二层目录：

```text
02-图像/提示词
02-图像/放大修复
02-图像/图像编辑
01-视频/综合
```

不要继续建立第三、第四层目录。技术细节应该由原笔记内容和已有 Tags 承担。

`config/bilibili-note-taxonomy.json` 中的 `routes` 只提供生成阶段的建议路径，不是 Organizer 的强制枚举表。Organizer 只限制目标目录最多两层，并禁止写回 `00-待整理` 或 `99-导航`。

---

## 3. 文件名怎么判断

文件名用于 Obsidian 文件列表、搜索和快速识别，因此应简短、直接，不承担摘要职责。

推荐在确有帮助时使用类型前缀：

- `百科：`：完整介绍某个模型、工具或体系；
- `教程：`：以操作方法为主；
- `工作流：`：围绕一套可复用流程；
- `实测：`：以测试结果、参数对比为主；
- `对比：`：多个方案或模型的横向比较。

例如原视频标题：

```text
Krea-2 百科全书：三十分钟了解这个速度快、AI味淡、生态繁荣的生图模型
```

可以只把文件名改成：

```text
百科：Krea-2 生图模型全解.md
```

笔记内部 H1 仍保持原样。

不要把章节目录重新塞进文件名，例如不需要写成：

```text
Krea-2 生图模型全解：版本选择、量化、提示词与生态玩法.md
```

---

## 4. 整理范围

范围共有三种：

- `single`：用户明确指定某一篇；
- `latest`：用户明确说“最近一篇”；Organizer 会验证它确实是 `00-待整理` 中最近的 Markdown 文件；
- `all`：用户明确要求整理全部待整理笔记。

用户已经明确指定文件时，直接使用 `single`，不要伪装成 `latest`。

只有用户只说“整理笔记”却没有给出对象时，才询问：

```text
要整理指定的一篇、最近一篇，还是全部待整理笔记？
```

---

## 5. Organizer 命令

统一入口只需要四类信息：原文件、目标文件名、目标目录、已确认范围。

```powershell
bili-learning organize `
  --note '<现有笔记路径>' `
  --filename '<新的简短文件名>' `
  --destination '<领域/对象>' `
  --confirmed-scope '<single|latest|all>'
```

示例：

```powershell
bili-learning organize `
  --note '<...>/00-待整理/Krea-2 百科全书....md' `
  --filename '百科：Krea-2 生图模型全解' `
  --destination '02-图像/Krea2' `
  --confirmed-scope single
```

Organizer 不接受 `--intro`、`--tag`、`--category`，因为归档阶段不再改写简介、Tags 或笔记内部结构。

同名目标已存在时不会覆盖，会自动使用 `（2）`、`（3）` 等序号。

---

## 6. 内容保护

Organizer 采用移动文件的方式归档，不重新序列化 Markdown 内容。

因此归档前后的文件内容应保持完全一致。唯一允许变化的是：

- 文件路径；
- 文件名；
- 自动生成的 `99-导航` 文件。

这意味着以下内容不会因为归档被二次加工：

```text
H1
Summary
正文
Frontmatter
Tags
视频简介
UP 主资源
原始说明
(workbuddy) / (GPT) 等测试标记
```

如果旧笔记格式需要升级，应由单独的迁移任务处理，不借 Organizer 顺手修改。

---

## 7. 重复 BVID

同一个 BVID 可以存在多个版本，例如不同 Agent / 模型的质量测试。

Organizer 会检测同 BVID 笔记并在返回值的 `duplicate_bvid_notes` 中提示，但：

- 不阻止归档；
- 不覆盖；
- 不自动删除；
- 不自动合并。

如果笔记元信息中带有 `(workbuddy)` 等标记，导航会保留该标记用于区分同标题测试稿。

---

## 8. Junction 路径

当 Obsidian Vault 通过 Windows Junction 指向仓库笔记目录时，同一个文件可能同时表现为逻辑 Vault 路径和真实磁盘路径。

Organizer 返回：

- `note_path`：配置中的逻辑路径；
- `resolved_note_path`：文件系统解析后的真实路径。

例如 `M:` 和 `G:` 同时出现并不代表重复写入。

---

## 9. 不做什么

学习后归档明确不负责：

- 优化正文；
- 重写摘要；
- 重写 H1；
- 补充视频简介；
- 修改 Tags；
- 自动迁移整棵历史目录；
- 合并重复 BVID；
- 删除测试版本。

需要这些操作时，应作为独立任务处理。
